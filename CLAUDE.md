## Commands

- `npm run dev` — start the dev server (persistent server typically already runs on `http://localhost:3000`; if the CLI reports a port conflict, target 3000 directly rather than starting a second instance on 3001)
- `npm run build` — production build
- `npm run start` — run a production build
- `npm run lint` — ESLint (flat config, `eslint-config-next`)
- `npx tsc --noEmit` — type-check only; run this after any non-trivial change, there is no separate test suite

There are no automated tests in this repo. `tsc --noEmit` is the correctness gate.

## Architecture

This is a single-page "OS-style portfolio" — a fake desktop environment rendered entirely client-side. `app/page.tsx` renders one component, `components/desktop/Desktop.tsx`, which owns almost all state and orchestrates everything else on the page (there is no routing beyond the root page).

**State ownership (`Desktop.tsx`)**
- `windows`: array of `OpenWindow` — `{ id, position, zIndex, origin?, maximized, minimized, transitionPhase, transitionTarget? }`. `topZ` is a `useRef` counter (not state) so bringing a window to front doesn't trigger extra re-renders. `iconPositions`: desktop icon positions, keyed by `IconId` (`"works" | "terminal"` — a narrower type than `WindowId`, since not every window has a corresponding desktop icon, e.g. `about`/`doc`).
- `iconLabelTone`: derived from `backgroundIndex` (dark-red/black backgrounds → `"light"` icon labels, everything else → `"dark"`) and passed to `DesktopIcon` so label/hover contrast stays readable across very different background colors.
- `backgroundIndex`: cycles through `BACKGROUND_COLORS` (rgb strings) and persists to `localStorage` (`vonnue-os-background-index`).
- `booted` / `shutdownActive` / `desktopCycle`: gate the boot/shutdown overlay animations. `desktopCycle` increments on every shutdown→reboot cycle and is folded into the desktop wrapper's `key` (`` key={`${booted}-${desktopCycle}`} ``) so the whole subtree remounts fresh after a reboot, resetting any lingering window/animation state.

Adding a new "window" (app) means: add its id to `WindowId`, add a title to `WINDOW_TITLES`, add static content to `WINDOW_CONTENT` (or special-case it in the `windows.map(...)` render like `Terminal`/`PdfViewer` are), and add a way to trigger `openWindow(id, origin?)` — either a `DesktopIcon` or a menu item (e.g. `about` has no desktop icon, only a `LogoMenu` entry — that's why `IconId` is narrower than `WindowId`).

**Window lifecycle & transitions (`WindowPanel.tsx`, `lib/windowTransition.ts`, `Desktop.tsx`)**
Every open/close/minimize/restore is a real FLIP-style Web Animations API animation (`element.animate(...)`, not CSS classes), computed from two `ViewportRect`s via `lib/windowTransition.ts`'s `calculateRectTransform`/`rectTransformToCss` — translate+scale from a rect matching the window's *previous* visual anchor to identity (or the reverse). This is why `OpenWindow.transitionPhase` (`"opening" | "open" | "preparing-minimize" | "minimizing" | "closing"`) exists and why it's a small state machine rather than a boolean:
- **Open**: `transitionPhase: "opening"`, animates from `origin` (the triggering icon's rect, passed up through `onOpen`) to identity; falls back to a plain fade/scale if no origin is available.
- **Close**: `closeWindow` sets `transitionPhase: "closing"` and computes `transitionTarget` via `resolveOriginalTarget` — the rect of whichever icon/button opened the window (tracked in `iconElements`/`docLauncherRef`, populated by `DesktopIcon`'s `onElement` callback prop), or a `pointTarget` fallback near the bottom-center. `WindowPanel` calls `onTransitionComplete` when its animation finishes, which `completeWindowTransition` uses to actually remove the window from state.
- **Minimize** is deliberately two-phase: `minimizeWindow` first sets `transitionPhase: "preparing-minimize"` (this makes `WindowPanel`'s transition effect early-return and do nothing that frame), waits two nested `requestAnimationFrame`s, then reads the eventual dock position and moves to `"minimizing"`. The double-rAF exists because the window can't measure the *real* `MinimizedDock` button yet — it isn't there (the window is still `!minimized`) — so `Desktop.tsx` also renders an invisible "shadow" dock (`data-minimize-transition-target`, `z-[-1]`, `pointer-events-none`, `invisible`) purely so its layout can be measured for the animation target *before* the real dock updates. Once the real animation finishes, `completeWindowTransition` flips `minimized: true`, the window drops out of the main render (`windows.filter(w => !w.minimized)`), and the real `MinimizedDock` picks it up.
- **Restore**: `MinimizedDock`'s `onRestore` calls `restoreWindow(id, origin)` with the clicked dock button's own rect as `origin`, re-entering at `"opening"`.
- **Maximize toggle** is handled entirely inside `WindowPanel` (`toggleMaximizeAnimated`), not the phase machine — it snapshots the pre-toggle rect into a ref and animates from it to identity in a separate `useLayoutEffect` keyed on the `fullscreen` (mobile-or-maximized) flag.

`MinimizedDock.tsx` runs its own small FLIP pass on every render (a `useLayoutEffect` diffing previous vs. current button rects) so existing dock items slide into their new slot when siblings are added or removed, instead of snapping.

**Dragging (`DesktopIcon.tsx`, `WindowPanel.tsx`)**
Both icons and window title bars use the same pattern for pointer-based dragging: `pointerdown` records a start position in a `useRef` (not state), then `pointermove`/`pointerup` are attached at the `window` level for the duration of the drag. `DesktopIcon` specifically mutates `buttonRef.current.style.left/top` directly on every `pointermove` and only commits to React state (`onMove`, which updates `Desktop`'s `iconPositions`) once on `pointerup` — going through `setState` on every move re-renders the whole desktop tree and visibly lags behind the cursor. Follow this direct-DOM-mutation-during-drag pattern for any new draggable element; don't call `setState` per-pointermove. Dragging (and the maximize toggle) is disabled while a window's `transitionPhase` is anything other than `"open"` (`transitionLocked` in `WindowPanel`) so you can't yank a window mid-animation.

**Mobile (`lib/useIsMobile.ts`)**
`useIsMobile()` (a `matchMedia('(max-width: 639px)')` hook, matching Tailwind's `sm` breakpoint) drives JS-level behavior branches that plain responsive classes can't express: `WindowPanel` switches from a floating panel to a non-draggable `inset-x-3 top-12 bottom-3` near-fullscreen panel (same `fullscreen` flag maximize uses), and `DesktopIcon` disables drag entirely so a tap calls `triggerOpen()` directly instead of select-then-double-click. Beyond that, the top bar and dropdowns just shrink via plain `sm:` Tailwind prefixes — no JS involved there.

Gotcha already hit once: never apply a CSS `transform` (including via a CSS animation, even one that ends at `scale(1)`/identity) to an ancestor of any `fixed`-positioned element here — nearly everything (`TopBar`, `DesktopIcon`, `WindowPanel`, `ChatWidget`, `MinimizedDock`) is `position: fixed` against the viewport, and a `transform` on an ancestor makes *that ancestor* the containing block instead. If the ancestor's own box isn't independently sized (e.g. a plain `<div>` wrapping only `fixed` children has ~zero natural height, since none of them contribute to normal flow), every descendant's `bottom-*`/`right-*`/viewport-relative math silently breaks. The boot→desktop `.crt-on` reveal in `Desktop.tsx` learned this the hard way — its wrapper is `fixed inset-0` specifically so it always equals the real viewport, not a collapsed box.

**Terminal (`Terminal.tsx`)**
Implements a small virtual filesystem (`FsFile` / `FsDir` / `FsNode` tagged union, built once as `ROOT` via `buildFs()`) with `resolvePath()`/`getNode()` supporting `.`, `..`, `~`, and absolute paths, backing the `ls`/`cd`/`cat`/`pwd` commands. Command output lines **must** keep `whitespace-pre-wrap` in the rendered `<div>` — without it, manually space-padded columns (e.g. in `help`) collapse and become unreadable; this was a real regression once already. `fillHeight` prop switches its own height from a fixed `sm:h-72` to `h-full` when its containing `WindowPanel` is maximized (see below).

**PDF viewer (`PdfViewer.tsx`)**
Renders `public/case1.pdf` with `pdfjs-dist` onto `<canvas>` (one `<PdfPage>` per page, each scaled to the container's measured width via `ResizeObserver`) rather than an `<iframe>` — gives consistent cross-browser rendering and keeps the window's sizing under CSS control instead of the browser's built-in PDF viewer chrome. The worker is loaded lazily (`import("pdfjs-dist")`, worker URL resolved via `new URL("pdfjs-dist/build/pdf.worker.min.mjs", import.meta.url)`) to keep it out of the main bundle. The `doc` window passes `WindowPanel` a custom `windowClassName` (`w-[80vw] h-[calc(45vw+37px)] ...`, keeping roughly a 16:9 content area — `45vw` ≈ half of `80vw * 9/16`, `+37px` accounts for the title bar) and `contentClassName="p-0"` — `WindowPanel` accepts both as overrides of its default `w-[420px] max-w-[calc(100vw-2rem)]` / `p-4` so per-window sizing doesn't need special-casing inside `WindowPanel` itself.

**Chat widget (`ChatWidget.tsx`)**
System messages (the initial greeting and each `AUTO_REPLIES` pick) reveal character-by-character via a `typing: { text, revealed }` state advanced on a `setTimeout` chain (not `setInterval`), reusing the `.cursor-blink` class as the trailing cursor; only committed to the real `messages` array once fully revealed. The greeting is queued the first time the panel actually opens — whether that's a manual click or the auto-open timer (currently 15s after mount, skipped if the user already interacted with the widget) — not on mount, so the typewriter effect is actually seen rather than finishing silently in the background. All `setState` calls in that effect happen inside the timeout callback, not synchronously in the effect body — `eslint`'s `react-hooks/set-state-in-effect` will flag it otherwise. Real message delivery is a `// TODO: wire real delivery through Resend once an API key exists` — not implemented, no credentials exist yet.

`ChatWidget` runs the same genie/FLIP open+close animation as `WindowPanel` (toward/from its own toggle button, using the same `lib/windowTransition.ts` helpers), with a `closing` state and an interruptible `panelAnimationRef` so reopening mid-close-animation doesn't glitch. It also plays a one-off `.chat-startup-in` CSS entrance when the widget itself first mounts (a separate, purely cosmetic "pop-in", distinct from the open/close panel animation).

`ChatWidget` is wrapped in `forwardRef` and exposes a `ChatWidgetHandle` (`{ openWithMessage(text) }`) via `useImperativeHandle` — this is the one place in the app that uses an imperative ref instead of props/lifted state, because `Desktop.tsx` needs to open the chat with a specific prompt from an arbitrary, unrelated trigger (`TopBar`'s "Report a Bug" menu item calls `Desktop`'s `reportBug()`, which calls `chatRef.current?.openWithMessage(...)`), and fully lifting the widget's chat state up to `Desktop` just to support that one call site isn't worth it.

**Styling**
Tailwind v4 (`@import "tailwindcss"` + `@theme inline` in `app/globals.css`), with all theme colors defined as CSS custom properties using `rgb()` notation (`--background`, `--foreground`, `--dim`, `--dimmer`, `--line`, `--accent`, `--accent-dim`) — keep new colors in this same `rgb()` form rather than hex, per existing convention. Border radius is force-reset to `0` globally (`* { border-radius: 0 !important; }`) to keep the flat/OS aesthetic — don't add rounded corners via inline styles either. The `.retro-scrollbar` class (used by `WindowPanel` content and the chat message list) gives scrollable panels a themed, chunky scrollbar — apply it to any new scrollable content for visual consistency. Accent colors on hover states/background cycling (`Desktop.tsx`'s `BACKGROUND_COLORS`, `Dropdown.tsx`'s trigger hover) get swapped out fairly often on request — they're plain arbitrary-value Tailwind classes (`bg-[rgb(r,g,b)]`), not theme tokens, by design. Note `LogoMenu`'s gradient trigger background is suppressed while its own dropdown is open (`triggerClassName={open ? "" : "bg-gradient-to-r ..."}`) so the open/hover state stays visible — it isn't unconditionally "always on".

**Config/data**
`lib/config.ts` holds `COMPANY_NAME` and `SOCIAL_LINKS`/`SITE_URL`, currently blank placeholders (intentionally not guessed — leave them blank unless given real values). `lib/time.ts` has two standalone utilities: `getWeightedClock()` (a stylized non-standard clock — day runs `-25` to `125` over 150 "hours"), used by `Terminal`'s `clock` command (the top-bar `Clock.tsx` itself now just renders a real wall clock via `Intl.DateTimeFormat`, ticking every 16ms), and `getYearProgress()`, used only by `Terminal`'s `date` command.
